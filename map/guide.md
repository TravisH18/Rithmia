You are going to build a Pathfinder-style interactive fantasy map as a **static, JS/TS-only feature** inside Docusaurus—no map server, database, or Earth-based basemap required. This is taking inspiration from pathfinders live map: https://map.pathfinderwiki.com/ and their github repo for the map: https://github.com/pf-wikis/mapping however, it will be web based, static inside the Docusaurus "rithmia" (The name of the planet you're creating a map for is Rithmia)

The core pattern is:

1. Create and maintain your fictional geography as vector data—primarily GeoJSON.
2. Render it in the browser with MapLibre GL JS (or, for a simpler map, Leaflet).
3. Add wiki-aware markers, labels, layers, popups, and deep links to Docusaurus pages.
4. When the dataset becomes large, compile GeoJSON into a single PMTiles archive and host it alongside the static site.

That is substantially the same architectural direction as PathfinderWiki’s project: it uses QGIS-managed geometry, GeoJSON for locations, MapLibre GL JS for the TypeScript frontend, and a generated PMTiles vector-tile file for efficient browser delivery. [github](https://github.com/pf-wikis/mapping)

## Recommended architecture

For your Docusaurus site, I would use **MapLibre GL JS + GeoJSON initially**, then move to PMTiles only if the map grows enough to justify it.

| Concern | Starter implementation | Scalable implementation |
|---|---|---|
| Browser renderer | MapLibre GL JS | MapLibre GL JS |
| World data | Separate GeoJSON files | PMTiles archive generated from GeoJSON/GeoPackage |
| Authoring tool | QGIS, with manually created layers | QGIS + version-controlled GeoPackage/GeoJSON |
| Hosting | Docusaurus static assets | Docusaurus static assets / object storage / CDN |
| Backend required? | No | No |
| Wiki connections | Feature property contains a Docusaurus route | Same, plus generated indexes/search |
| Interactivity | Click popups, filters, layer toggles, fly-to links | Same |
| Best at | A few hundred to a few thousand features | Large coastlines, detailed borders, many labels/features |

MapLibre GL JS is a WebGL map renderer intended for browser-based interactive maps. It can consume GeoJSON directly, including points, lines, and polygons, and it internally prepares GeoJSON for tiled rendering. [maplibre](https://www.maplibre.org/maplibre-gl-js/docs/API/classes/GeoJSONSource/)

### What “JS/TS only” means

You can deploy this as fully static HTML/CSS/JS generated by Docusaurus:

- **No Node server at runtime**
- **No GIS tile server**
- **No PostGIS database**
- **No third-party maps API key**, if you draw all map content yourself
- **No Earth data or coordinate lookup necessary**

You might still use local tooling during authoring/build time—QGIS, Node scripts, or Tippecanoe—to produce data files. But your public site can remain static.

For a fictional world, you are not using geographic truth; you are using geographic *conventions*: coordinates, geometry, zoom levels, layers, styling rules, and spatial queries. Those work equally well for an invented planet, continent, moon, underworld, or planar realm.

## Create a fictional GIS world

A GIS map is fundamentally a collection of shapes with attributes. Your world could be represented using layers like these:

| Layer | Geometry | Example attributes |
|---|---|---|
| `landmasses` | Polygon / MultiPolygon | `id`, `name`, `wikiPath`, `biome`, `culture` |
| `water` | Polygon | `name`, `type`, `depthClass` |
| `rivers` | LineString | `name`, `width`, `navigable` |
| `mountain_ranges` | LineString or Polygon | `name`, `heightClass`, `terrain` |
| `kingdoms` | Polygon | `name`, `ruler`, `wikiPath`, `color` |
| `roads` | LineString | `name`, `roadType`, `condition` |
| `settlements` | Point | `name`, `kind`, `population`, `wikiPath` |
| `sites` | Point | `name`, `siteType`, `wikiPath`, `discovered` |
| `labels` | Point | `text`, `fontScale`, `category`, `minZoom` |

A settlement in GeoJSON might look like this:

```json
{
  "type": "Feature",
  "id": "everspring",
  "properties": {
    "name": "Everspring",
    "kind": "City",
    "population": 42000,
    "wikiPath": "/locations/everspring",
    "faction": "The Verdant Compact"
  },
  "geometry": {
    "type": "Point",
    "coordinates": [2800, 1640]
  }
}
```

For a completely made-up world, those coordinates can simply be your own abstract map units. A coordinate of `[2800, 1640]` does **not** have to mean longitude and latitude.

### Coordinate-system choices

There are two reasonable paths.

**Option A — Use normal longitude/latitude-style numbers.**  
Treat your world map as if it occupies a fictional rectangle such as longitude \(-180\) to \(180\), latitude \(-90\) to \(90\). This is convenient because most web-map libraries expect WGS84-style coordinates.

- Easy to integrate with MapLibre.
- Easy to use GeoJSON directly.
- You must accept Web Mercator’s familiar distortion near “poles.”
- A strong choice for an overview world map with a mostly rectangular extent.

**Option B — Use custom planar coordinates.**  
Use coordinates such as \(0 \ldots 10{,}000\) in X and Y, like a game world or CAD canvas.

- Intuitive if you think in miles, hexes, pixels, or map units.
- Ideal for a single continent/world illustration.
- Usually requires a custom projection/setup or using an image-coordinate-oriented approach.
- Best when your source is a hand-drawn map and geographic projection realism is unimportant.

For a first production version, I recommend **Option A** even for an invented setting. You get the web-map ecosystem’s defaults while retaining complete artistic and geographical control.

## Authoring workflow

### 1. Start with a world design source

You have several good choices depending on whether you want procedural generation or deliberate cartographic control.

**Azgaar’s Fantasy Map Generator** is the most natural starting point if you want it to generate coastlines, heightmaps, states, cultures, rivers, burgs, routes, and labels. It can export GeoJSON for cells, routes, rivers, markers, and zones, and the exported data is intended to be usable in GIS applications such as QGIS. [github](https://github.com/Azgaar/Fantasy-Map-Generator/wiki/GIS-data-export)

A productive workflow would be:

1. Generate rough world geography in Azgaar.
2. Save its native project format so you can return to the editable generator project.
3. Export the useful GIS layers as GeoJSON.
4. Load those layers into QGIS.
5. Simplify/redraw what should be canonical lore rather than procedural output.
6. Add manual features: named roads, political borders, ruins, settlements, regions, sea routes, and article links.
7. Export versioned GeoJSON files for the Docusaurus app.

If you prefer to hand-design the map:

1. Draw your map in Krita, Photoshop, Procreate, Inkarnate, Wonderdraft, or a vector editor.
2. Use the image as a **non-authoritative visual reference**.
3. In QGIS, create vector layers over it and trace coastlines, rivers, kingdoms, and roads.
4. Store lore-relevant entities as feature attributes rather than burying them in pixels.

That is close to the PathfinderWiki approach: they georeference visual source maps and manage vector geometry—landmasses, water, rivers, borders, labels—in QGIS, while locations are maintained as GeoJSON. [github](https://github.com/pf-wikis/mapping)

### 2. Use QGIS as the canonical editor

QGIS works well here even when none of your data corresponds to Earth. It is not just for satellite imagery or public map layers; it is a powerful editor for points, lines, polygons, labels, relationships, attributes, and exports.

A useful source-of-truth project layout might be:

```text
world-map/
  qgis/
    my-world.qgz
  data/
    landmasses.geojson
    water.geojson
    rivers.geojson
    borders.geojson
    roads.geojson
    settlements.geojson
    sites.geojson
    labels.geojson
  styles/
    map-style.json
  public/
    map/
```

Keep a stable identifier on every feature:

```text
id: settlement-everspring
wikiPath: /locations/everspring
```

Do **not** key relationships solely on display names. Names change; IDs should not.

### 3. Treat vector geometry and artwork separately

This is an important design decision.

- **Vector data** is interactive: land boundaries, routes, regions, markers, filters, popups, tooltips, article navigation.
- **Raster artwork** supplies atmosphere: parchment texture, hand-drawn mountains, shaded relief, watercolor seas, illustrated forests.

You can combine both:

- Put a parchment or fantasy map image beneath the vector layers.
- Draw interactive borders, settlements, labels, and routes on top.
- Let the vector data be your source of truth for interactivity.
- Re-export the artwork whenever you make a major artistic revision.

This gives you the visual character of a traditional fantasy map without sacrificing queryable layers and clickable wiki integration.

## Integrate it with Docusaurus

Create a normal React page such as:

```text
src/pages/map.tsx
```

Then place public map data in:

```text
static/map/data/
```

Anything in Docusaurus’s `static/` directory is copied into the built site. That lets you load map data by paths such as `/map/data/settlements.geojson`.

Install the browser dependencies:

```bash
npm install maplibre-gl
```

A minimal `src/pages/map.tsx` could look like this:

```tsx
import React, { useEffect, useRef } from "react";
import Layout from "@theme/Layout";
import maplibregl from "maplibre-gl";
import "maplibre-gl/dist/maplibre-gl.css";

export default function WorldMapPage() {
  const mapNode = useRef<HTMLDivElement>(null);

  useEffect(() => {
    if (!mapNode.current) return;

    const map = new maplibregl.Map({
      container: mapNode.current,
      center: [0, 20],
      zoom: 2,
      minZoom: 1,
      maxZoom: 8,
      style: {
        version: 8,
        sources: {
          land: {
            type: "geojson",
            data: "/map/data/landmasses.geojson"
          },
          settlements: {
            type: "geojson",
            data: "/map/data/settlements.geojson"
          }
        },
        layers: [
          {
            id: "land-fill",
            type: "fill",
            source: "land",
            paint: {
              "fill-color": "#d3b57d",
              "fill-outline-color": "#5c4426"
            }
          },
          {
            id: "settlement-symbols",
            type: "symbol",
            source: "settlements",
            layout: {
              "icon-image": "marker-15",
              "icon-size": 1.1,
              "text-field": ["get", "name"],
              "text-offset": [0, 1.2],
              "text-anchor": "top"
            },
            paint: {
              "text-color": "#2b1d12"
            }
          }
        ]
      }
    });

    map.on("click", "settlement-symbols", (event) => {
      const feature = event.features?.[0];
      const wikiPath = feature?.properties?.wikiPath;

      if (wikiPath) {
        window.location.assign(wikiPath);
      }
    });

    map.on("mouseenter", "settlement-symbols", () => {
      map.getCanvas().style.cursor = "pointer";
    });

    map.on("mouseleave", "settlement-symbols", () => {
      map.getCanvas().style.cursor = "";
    });

    return () => map.remove();
  }, []);

  return (
    <Layout title="World Map">
      <main style={{ height: "calc(100vh - 60px)" }}>
        <div ref={mapNode} style={{ height: "100%", width: "100%" }} />
      </main>
    </Layout>
  );
}
```

The exact styling will evolve, but the key concepts are stable:

- `addSource` / `sources` load your data.
- `layers` decide how polygons, roads, symbols, and labels render.
- Each map feature can contain metadata such as a wiki route.
- A click handler can navigate to a Docusaurus document.
- The map can also read URL query parameters and fly to a specified place.

### Add bidirectional wiki links

Your setting pages should link back to the map:

```md
---
title: Everspring
map:
  featureId: settlement-everspring
---

Everspring is the capital of the Verdant Compact.

[View on the world map](/map?feature=settlement-everspring)
```

Then have your map page inspect `feature=...`, find that GeoJSON feature, and call `map.flyTo(...)`.

That gives you a satisfying bidirectional loop:

- A map marker opens the lore page.
- A lore page can open the map focused on that feature.
- Regions can show all subordinate settlements.
- Faction pages can filter the map to their territory and associated sites.
- Historical-era pages can toggle dated borders, roads, ruins, or place names.

## Scale with PMTiles later

Start with GeoJSON. It is easy to inspect in Git, easy to edit with QGIS, and easy to debug in the browser.

Once your world has highly detailed coastlines, dense labels, hundreds of points, or multiple eras/layers, convert your exported data to vector tiles and package it as **PMTiles**.

PMTiles is designed to be read directly by MapLibre in the browser. The archive can be hosted as a static file; the browser requests only the byte ranges/tiles it needs.  This is the key to avoiding a tile server. [maplibre](https://www.maplibre.org/maplibre-gl-js/docs/examples/pmtiles-source-and-protocol/)

The Pathfinder project compiles its GIS layers into a PMTiles file and renders it through a MapLibre TypeScript frontend. [github](https://github.com/pf-wikis/mapping)

Your production pattern would become:

```text
QGIS / GeoPackage / GeoJSON
          ↓
     tile-generation build step
          ↓
       world.pmtiles
          ↓
Docusaurus static hosting + MapLibre + pmtiles JS library
```

On the frontend, the source becomes conceptually similar to:

```ts
import * as maplibregl from "maplibre-gl";
import { Protocol } from "pmtiles";

const protocol = new Protocol();
maplibregl.addProtocol("pmtiles", protocol.tile);

const map = new maplibregl.Map({
  container: "map",
  style: {
    version: 8,
    sources: {
      world: {
        type: "vector",
        url: "pmtiles:///map/world.pmtiles"
      }
    },
    layers: [
      {
        id: "land",
        type: "fill",
        source: "world",
        "source-layer": "landmasses",
        paint: { "fill-color": "#c9ae72" }
      }
    ]
  }
});
```

For a static host, confirm that it supports HTTP range requests for `.pmtiles` files. PMTiles works through such range requests, allowing a single archive to function as a tiled data source without a conventional dynamic tile service. [docs.protomaps](https://docs.protomaps.com/pmtiles/maplibre)

## A practical build plan

### Phase 1: Make a compelling first map

- Use Azgaar to generate a first-pass continent or world, or create hand-drawn geography.
- Commit the original source file to your map repository.
- Export or create GeoJSON for:
  - Land and water
  - Rivers
  - Political regions
  - Settlements
  - Important sites
- Build one Docusaurus `/map` page with MapLibre.
- Make settlement markers open corresponding Docusaurus documents.

Do not start with terrain shaders, generated labels, multiple projections, or tiles. Get an attractive overview map with clickable lore locations working first.

### Phase 2: Establish maintainable lore data

- Make feature IDs permanent.
- Add `wikiPath`, `era`, `faction`, `tags`, and `visibility` attributes.
- Generate locations from markdown front matter if you want the wiki to become the canonical source for point locations.
- Keep boundaries, rivers, and roads in GIS files rather than in article front matter.
- Add map filters: political era, faction, settlement type, culture, religion, trade routes, or “known versus unexplored.”

For example:

```yaml
---
title: Everspring
mapId: settlement-everspring
mapCoordinates: [2800, 1640]
settlementType: city
faction: verdant-compact
era: third-age
---
```

A small build script can scan Docusaurus Markdown/MDX front matter and generate `settlements.geojson`. That eliminates duplicate entry of coordinates and makes the documentation itself drive the map’s point-of-interest layer.

### Phase 3: Improve visual cartography

- Use a custom MapLibre style palette: parchment, ink, muted regional fills, sea hatching.
- Add SVG icons for settlement classes, ruins, dungeons, ports, capitals, temples, and dangerous areas.
- Add hover cards that summarize a location without leaving the map.
- Add a detail panel rather than navigating immediately on click.
- Use a raster underlay for illustrated terrain.
- Add separate layers for borders by era or map mode.

### Phase 4: Tile and optimize

- Simplify very detailed geometries at smaller zoom levels.
- Use PMTiles if raw GeoJSON payloads become noticeably large.
- Split public and spoiler content into different files/layers, particularly useful if players and GM-facing material coexist.
- Generate searchable metadata for place-name search and a “fly to location” command palette.

## Inkarnate to Usable GeoJSON guide using QGIS
Yes—but it is not an automatic “convert image to GIS” operation in the general case. Your Inkarnate export is a **raster image**: it contains colored pixels, including decorative labels and terrain art, but it does not inherently know that a particular outline is a coastline, that a stroke is a road, or that “Everspring” belongs at a specific coordinate.

The normal and best workflow is to use your existing Inkarnate map as a visual base layer, assign it a consistent fictional coordinate system, then **trace and annotate only the features you need** as GIS vector layers in QGIS. You keep the image for the cartographic art and use GeoJSON for the interactive data. QGIS’s editing workflow supports creating point, line, and polygon layers and digitizing features by clicking them directly over a raster reference. [maps.nls](https://maps.nls.uk/projects/urbhist/guides_vectorlayerqgis.html)

## The recommended approach

For a Docusaurus fantasy wiki, I would use this hybrid model:

```text
Inkarnate PNG/JPG
  └─ visual background / terrain artwork

QGIS-maintained vector data
  ├─ land / coastlines              → polygons
  ├─ political regions              → polygons
  ├─ rivers and roads               → lines
  ├─ settlements and landmarks      → points
  └─ labels / wiki metadata         → point features with properties

Docusaurus + MapLibre
  └─ raster image underneath + interactive GeoJSON above
```

That prevents you from trying to duplicate every hand-painted Inkarnate feature in vector form. At first, digitize only what benefits the website:

- Clickable settlements and landmarks.
- Named regions and political borders.
- Important routes and rivers.
- Dungeon, ruin, quest, faction, and historical-event locations.
- Any place with a corresponding Docusaurus wiki page.

You can add more geometry later. A highly detailed coastline or every illustrated tree is normally not worth tracing unless it supports a map feature you actually need.

## Give your image coordinates

Since this is not Earth, you first need to decide how pixel positions map to fictional coordinates. You have two good options.

### Option 1: Use a simple made-up map grid

This is probably the best starting point for you.

Suppose your Inkarnate export is 8,000 × 5,000 pixels. You could define its map-space extent as:

```text
Top-left:      [-180,  90]
Top-right:     [ 180,  90]
Bottom-right:  [ 180, -90]
Bottom-left:   [-180, -90]
```

Those coordinates do **not** mean Earth longitude and latitude in your setting. They are simply numbers that work nicely with web-map libraries. Your map occupies a conventional rectangle, and every settlement, region, and road gets a coordinate in that rectangle.

This is convenient because GeoJSON and MapLibre naturally expect coordinate pairs in longitude/latitude form. Your fantasy map can use those conventions without representing real geography.

### Option 2: Use image-space coordinates

Alternatively, define the map as:

```text
Top-left:      [0, 5000]
Top-right:     [8000, 5000]
Bottom-right:  [8000, 0]
Bottom-left:   [0, 0]
```

This aligns data directly with image pixels, so a location at image pixel `(x=3000, y=1200)` can be transformed into your map coordinate system.

This approach can be extremely intuitive while authoring, but can require more projection/custom-coordinate work in MapLibre. It is easier to do with Leaflet’s `CRS.Simple`; however, because you want a Pathfinder-like map that may grow over time, I would still favor MapLibre with a conventional \(-180 \ldots 180\), \(-90 \ldots 90\) fictional extent.

## Set up the map in QGIS

You do **not** need actual georeferencing to Earth. You are simply establishing a coordinate system for your own world.

### 1. Preserve the original Inkarnate image

Keep your original high-resolution export outside the Docusaurus project or in an authoring repository. Your `static/imgs/...` copy can be the web-facing artifact, but it is wise to retain:

- The original Inkarnate project, if available.
- A high-resolution PNG export.
- An optimized web version for the website.
- Any alternate versions—political, physical, historical-era, GM-only, and player-safe.

Do not try to make the static web image the sole source of truth. It is your illustration layer, not your structured geographic dataset.

### 2. Create a QGIS project

In QGIS:

1. Create a new blank project.
2. Set the project CRS to `EPSG:4326` / WGS 84.
3. Add your Inkarnate PNG as a raster layer via **Layer → Add Layer → Add Raster Layer**.
4. Open **Raster → Georeferencer**.
5. Load your Inkarnate image into the Georeferencer.

QGIS’s Georeferencer aligns an otherwise unreferenced raster or vector layer to a coordinate system using ground control points. For a fictional map, you manually define those reference points rather than matching recognizable Earth locations. [docs.qgis](https://docs.qgis.org/latest/en/docs/user_manual/managing_data_source/georeferencer.html)

### 3. Add four fictional control points

Use the four corners of the map image as Ground Control Points (GCPs):

| Inkarnate image corner | Fictional coordinate |
|---|---:|
| Top-left | `[-180, 90]` |
| Top-right | `[180, 90]` |
| Bottom-right | `[180, -90]` |
| Bottom-left | `[-180, -90]` |

In the QGIS Georeferencer:

1. Click **Add GCP Point**.
2. Click exactly on the top-left corner of your image.
3. Enter X = `-180`, Y = `90`.
4. Repeat for the other three corners.
5. Select a simple transformation such as **Linear** or **Helmert**.
6. Set target CRS to `EPSG:4326`.
7. Choose GeoTIFF for the output image, e.g. `world-georeferenced.tif`.
8. Run the process and load the result into the QGIS project.

The Georeferencer supports manually entering X/Y coordinates for a control point and exporting a transformed raster. [docs.qgis](https://docs.qgis.org/latest/en/docs/user_manual/managing_data_source/georeferencer.html)

Because the source image is a flat rectangular export, four precisely placed corner points should be sufficient. You are not correcting aerial-photo distortion; you are mapping a rectangle to another rectangle.

### 4. Verify orientation before tracing

Confirm the output looks right:

- North is at the top, unless your map deliberately uses a different orientation.
- The full image appears in the expected rectangular extent.
- QGIS’s coordinate readout changes meaningfully as you move across the map.
- Your future vector layers will overlay the image correctly.

If the image appears rotated, mirrored, or vertically inverted, correct it before digitizing. This is much easier than reversing hundreds of feature coordinates later.

## Create GeoJSON layers by tracing

Your image is now just a backdrop. Next, create actual editable GIS vector layers.

I recommend using a **GeoPackage** (`world.gpkg`) as the local source of truth. GeoPackage stores multiple layers in one portable file and is generally more maintainable than a pile of shapefiles. QGIS can create GeoPackage layers as well as Shapefile and other formats. [docs.qgis](https://docs.qgis.org/latest/en/docs/user_manual/managing_data_source/create_layers.html)

Use this initial layer layout:

| Layer | Geometry | Minimum properties |
|---|---|---|
| `settlements` | Point | `id`, `name`, `kind`, `wikiPath`, `importance` |
| `landmarks` | Point | `id`, `name`, `kind`, `wikiPath`, `tags` |
| `regions` | Polygon | `id`, `name`, `wikiPath`, `faction`, `color` |
| `borders` | LineString | `id`, `name`, `regionLeft`, `regionRight`, `era` |
| `rivers` | LineString | `id`, `name`, `navigable`, `wikiPath` |
| `roads` | LineString | `id`, `name`, `roadType`, `condition` |
| `coastline` | Polygon / MultiPolygon | `id`, `name`, `kind` |
| `map_labels` | Point | `text`, `kind`, `minZoom`, `fontSize` |

### Start with settlements

This delivers the most visible result for the least effort.

1. Choose **Layer → Create Layer → New GeoPackage Layer**.
2. Set geometry type to **Point**.
3. Add fields such as:
   - `id` — text; stable internal ID.
   - `name` — text; public display name.
   - `kind` — text; `capital`, `city`, `town`, `village`, `ruin`, `dungeon`, etc.
   - `wikiPath` — text; e.g. `/locations/everspring`.
   - `importance` — integer; controls icon scale/label visibility.
4. Enable snapping if you want consistent attachment to roads, coastlines, or region edges.
5. Toggle editing.
6. Select the **Add Point Feature** tool.
7. Click each location on its illustrated position.
8. Fill in its attributes.
9. Save edits.

QGIS digitizing works by selecting the target geometry type, clicking to capture a point or successive points for a line/polygon, and then saving the edited layer. [maps.nls](https://maps.nls.uk/projects/urbhist/guides_vectorlayerqgis.html)

A city feature should eventually resemble:

```json
{
  "type": "Feature",
  "id": "settlement-everspring",
  "properties": {
    "id": "settlement-everspring",
    "name": "Everspring",
    "kind": "capital",
    "importance": 5,
    "wikiPath": "/locations/everspring",
    "faction": "verdant-compact"
  },
  "geometry": {
    "type": "Point",
    "coordinates": [-42.72, 18.31]
  }
}
```

Those coordinates are entirely yours. What matters is their stable relationship to the background map and to every other feature.

### Trace lines and polygons selectively

Once points work, add features only when they have a purpose.

- **Rivers**: create a LineString layer; click along the visible river path, using more vertices only where it curves.
- **Roads**: create another LineString layer; use attributes for paved road, trail, imperial highway, sea route, etc.
- **Kingdoms/regions**: create a Polygon layer; click around the border and right-click to finish the polygon.
- **Landmasses**: create polygons only if you need area click behavior, coastline coloring, biome overlays, or to hide/show territory dynamically.

For polygons and lines, QGIS allows you to capture successive vertices; snapping can keep adjacent features aligned rather than leaving tiny gaps or overlaps. [docs.qgis](https://docs.qgis.org/latest/en/docs/user_manual/working_with_vector/editing_geometry_attributes.html)

### Avoid duplicate labels at first

Your Inkarnate map already has place names. If you draw labels from GeoJSON immediately, visitors will see doubled text.

Initially, consider rendering only:

- Small clickable icons/circles.
- Hover highlights.
- Region boundary outlines.
- A pop-up or side panel.
- Search results that pan/zoom to a point.

Then, if you later create a clean unlabeled Inkarnate export, you can enable GeoJSON-driven labels and gain responsive label sizing, filtering, localization, era toggles, and collision management.

## Map image limits

A single Inkarnate image as a MapLibre image source is excellent for an initial interactive map, but has limits:

- Large PNG files can make initial page load slow.
- Raster labels become blurry when users zoom in past the image’s native resolution.
- You cannot selectively hide labels, terrain symbols, or borders baked into the image.
- GIS overlays will not automatically match every decorative illustrated detail.
- A high-detail continental or world map may eventually need tiled raster imagery.

For a world map at moderate zoom, a high-quality WebP background plus GeoJSON overlays is typically sufficient. Start there rather than prematurely building tiles.

If it becomes too large, create multiple zoom-oriented image exports or convert the base art into raster tiles. Your vector GeoJSON layer design remains valid either way.

## What cannot be reliably automated

There are image-processing approaches that can detect color regions, lines, or OCR-readable labels, but they are usually poor as a final fantasy GIS workflow:

- Inkarnate coastlines are textured and shaded rather than clean mathematical boundaries.
- Rivers, roads, and contour-like art can visually overlap.
- Decorative labels may have curved text, ornate fonts, outlines, and effects.
- Automatic OCR does not know whether a label refers to a city, kingdom, river, or mountain range.
- Automatic tracing tends to yield noisy, excessive vertices and poor topology.

You could use OCR as a **data-entry assistant** for a heavily labeled map, but manually verify every location and place it by hand. For your own map, manual digitization is almost certainly faster than correcting automatically extracted data and gives you data that matches your lore model from the beginning.

## A lean first milestone

Build this before attempting an all-feature conversion:

1. Georeference the Inkarnate image in QGIS against your fictional \(-180 \ldots 180\), \(-90 \ldots 90\) extent.
2. Create a `settlements` point layer with ten to twenty important places.
3. Add a stable `id`, a human-readable `name`, a `kind`, and a Docusaurus `wikiPath` to each point.
4. Export that one layer to GeoJSON.
5. Add the Inkarnate image as the MapLibre background.
6. Overlay clickable settlement markers.
7. Make marker click open your corresponding Docusaurus article.
8. Add `View on map` links in the relevant wiki articles.

That will prove the full pipeline and give your setting a useful interactive map quickly. After that, tracing regions, trade routes, rivers, historical borders, travel overlays, and era-specific views becomes an incremental content project rather than a large technical rewrite.

QGIS can classify image pixels and convert contiguous same-class regions into polygons using GDAL’s **Polygonize (Raster to Vector)** tool. It will not inherently understand “this is the coastline”; it will identify groups of pixels sharing a value or falling within a chosen color range. That can produce a useful first-pass land polygon if your ocean is relatively uniform, but a typical textured Inkarnate map will need cleanup afterward. [docs.qgis](https://docs.qgis.org/latest/en/docs/user_manual/processing_algs/gdal/rasterconversion.html)

## When it works well

Automatic/semi-automatic tracing is promising when your export has:

- One largely consistent ocean or sea color.
- Land that strongly contrasts with water.
- Few waves, labels, borders, glow effects, decorative frames, or parchment textures touching the coastline.
- A high-resolution source image.
- A coastline you want as a broad interactive extent rather than exact pixel-perfect replication.

For example, if the water is mostly a dark blue/teal and land is tan/green/brown, you can classify “water-like pixels,” make a binary water/land raster, and polygonize it. The resulting boundary becomes a coastline candidate.

QGIS/GDAL’s polygonization process makes polygons from connected raster regions with common pixel values; pixels that are diagonally touching can optionally be considered connected as well. [docs.qgis](https://docs.qgis.org/latest/en/docs/user_manual/processing_algs/gdal/rasterconversion.html)

## Why an Inkarnate JPEG is difficult

A JPEG usually makes automated coastline extraction worse than a clean PNG because JPEG compression alters colors around edges. More importantly, Inkarnate maps commonly include:

- Gradient water coloration, waves, foam, and shoreline shading.
- Texture, shadows, and glow around land.
- Mountains, trees, roads, text labels, and icons.
- Islands and inland lakes.
- Decorative map borders or legends.

Those features can cause either of two bad outcomes:

- Water is broken into many disconnected color patches, producing thousands of tiny polygons.
- Coastal land colors get classified as water—or vice versa—creating ragged, inaccurate coastlines.

So the right expectation is: **automatic classification can give you a draft polygon; manual editing makes it usable.** For a modest number of continents/islands, manually tracing the coastline in QGIS may actually be faster and cleaner than repeatedly tuning image classification.

## Best practical workflow

Use the automatic route only if a quick test produces a recognizable coastline in 10–20 minutes. Otherwise, switch to manual digitizing.

### 1. Prefer a clean export

If you can re-export from Inkarnate, make a version optimized for extraction:

- Export as **PNG**, not JPEG.
- If possible, turn off labels, decorative frames, compass roses, parchment texture, and legends.
- Use simple/consistent ocean color.
- Reduce or remove waves, coastline glow, foam, and shading.
- Keep the same canvas dimensions and boundaries as the web image.

You do not need to use this clean export as the public map background. It can be an internal “tracing source” only. Your public site can still show the polished JPEG/PNG artwork.

### 2. Georeference it first

Use the same fictional extent that you plan to use in MapLibre, for example:

```text
Top-left:      [-180,  90]
Top-right:     [ 180,  90]
Bottom-right:  [ 180, -90]
Bottom-left:   [-180, -90]
```

Then any coastline vectors you create will align with the exact image displayed on the website.

QGIS’s Georeferencer aligns an otherwise unreferenced image with a chosen coordinate system through manually placed ground-control points. For your map, the four image corners serve as fictional control points. [docs.qgis](https://docs.qgis.org/latest/en/docs/user_manual/managing_data_source/georeferencer.html)

### 3. Create a land/water mask

The goal is not to directly polygonize a colorful JPEG. The goal is first to create a **binary mask**:

```text
Land pixel  → 1
Water pixel → 0
```

There are several ways to do that in QGIS.

#### Simplest: color-based selection/classification

Use a plugin or raster-classification workflow that lets you sample colors from the ocean, tune a tolerance, and preview the selected pixels.

The QGIS Raster Vectorizer plugin is designed for raster-to-polygon conversion through interactive HSV color-range classification: sample colors, adjust tolerance, apply cleanup operations, then polygonize. It explicitly supports JPEG, PNG, and GeoTIFF inputs. [plugins.qgis](https://plugins.qgis.org/plugins/raster_vectorizer/)

For your map, sample a few representative water areas:

- Open ocean.
- Darker ocean.
- Lighter ocean.
- Coastal water outside the foam/shadow zone.

Then expand the selected HSV range just enough to include the water while excluding obvious land.

#### More involved: supervised classification

The Semi-Automatic Classification Plugin can help classify image regions using training areas. It is principally a remote-sensing tool, but the same principle applies: mark representative water and land samples, run a classification, then turn the classified output into vector geometry. Its purpose is to support semi-automatic image classification and subsequent raster/vector workflows. [plugins.qgis](https://plugins.qgis.org/plugins/SemiAutomaticClassificationPlugin/)

For an Inkarnate map, this is usually overkill unless you are comfortable doing image classification or the land/water color separation is unusually clean.

### 4. Clean the mask before polygonizing

Before converting the mask to vectors, use raster cleanup steps to remove noise:

- **Majority/median filter** to remove isolated pixels.
- Morphological cleanup to fill small holes or remove specks.
- Reclassification so you retain only `land = 1` and `water = 0`.
- Crop/mask out legends, borders, scale bars, and title cartouches.
- Optionally manually paint troublesome areas in an image editor before the QGIS workflow.

This is the stage that determines whether you get one clean continent polygon versus a huge number of fragmented polygons.

### 5. Run Polygonize

In QGIS Processing Toolbox, search for:

```text
Polygonize (Raster to Vector)
```

Select your binary land/water mask, choose the band containing your land/water values, and enable 8-connectedness if diagonal pixel contact should be treated as continuous. QGIS’s Polygonize algorithm creates vector polygons from connected cells of the same raster value and attaches the pixel/class value as an attribute. [docs.qgis](https://docs.qgis.org/latest/en/docs/user_manual/processing_algs/gdal/rasterconversion.html)

After it runs:

1. Filter the output to retain only the land class, such as `DN = 1`.
2. Delete clearly unwanted polygons—legend fragments, accidental specks, decorative features.
3. Dissolve contiguous land areas if appropriate.
4. Fix inland water holes and islands according to your setting’s intended geography.
5. Simplify the geometry.
6. Manually reshape and edit important coastline areas.

## Essential post-processing

The raw coastline from a raster will be overly detailed because it follows individual pixels. Even a good result will need vector cleanup.

Use these QGIS tools after polygonizing:

| Task | Typical QGIS operation |
|---|---|
| Keep only land | Filter by the polygonized class-value field |
| Merge adjacent fragments | Dissolve |
| Remove tiny false islands/specks | Delete manually or filter by area |
| Smooth pixel stair-steps | Smooth geometry |
| Reduce excessive vertices | Simplify |
| Repair invalid self-intersections | Fix geometries |
| Correct major coastline errors | Toggle editing and move/add/delete vertices |
| Preserve proper islands/lakes | Edit polygons and their holes manually |

Be deliberate with **Simplify**: zoom out and validate the result against the original art. You want fewer vertices for browser performance, but not a coastline that visibly loses its character.

A good target is a clean polygon that resembles the shoreline at the maximum zoom level you intend to support—not a geometry that reproduces every JPEG artifact.

## An alternate approach that is often better

If your goal is an interactive fantasy map rather than a GIS exercise, I would normally trace the coastline manually—using a clean export as the QGIS backdrop—and reserve automatic work for **points** or very broad region masks.

Why manual tracing can win:

- You only need a moderate number of vertices around each landmass.
- You control which bays, islands, lakes, and channels matter to the lore.
- You avoid taking decorative coastline effects literally.
- You create clean geometry suitable for browsers and Git.
- You can finish one continent in a focused session instead of troubleshooting classification artifacts.

Use automatic polygonization as an accelerator: generate a rough candidate, simplify it aggressively, then edit it until it is canonically correct.

## Suggested decision tree

- **Flat water color, crisp coast:** Try HSV/color classification → clean mask → polygonize.
- **Moderate texture but obvious land/water difference:** Try automatic extraction once, then plan significant manual cleanup.
- **Heavy parchment texture, waves, labels, terrain shading, and ornate coasts:** Trace manually in QGIS.
- **You can make a clean Inkarnate export:** Use that internal source for automated extraction or easy tracing; retain the polished image for the Docusaurus display.
- **You only need interactive cities/places right now:** Skip coastline vectorization entirely; put your background image in MapLibre and start by digitizing clickable settlement points.

In short: QGIS can automate the mechanical raster-to-polygon part, but it cannot reliably infer the intended cartographic coastline from a styled Inkarnate JPEG. A clean PNG/map variant plus semi-automatic classification is the best automation route; a manually reviewed and simplified vector coastline is the best final result.
